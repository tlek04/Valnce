# 공격·중복·빠른 조작 추가 점검

기준: 2026-11-07. 애플리케이션 코드·기능·UI는 수정하지 않았다. 실제 Worker 소스와 스토어를 실행하고 메모리 KV의 읽기/쓰기 타이밍을 조절해 요청 교차를 재현했다. 운영 서버에 공격 요청이나 부하를 보내지 않았다. 운영 WAF 설정, 실제 분산 KV의 지연과 발생 빈도는 확인하지 않았다.

재현 명령: `node .test-cache/security-review.mjs`. 이전 점검 재현은 `node .test-cache/review-audit.mjs`.

## 결론

순차 요청과 단일 화면 조작에 대한 일부 방어는 있지만, 동시 요청·응답 순서 역전·익명 사용자 신원 확인에 대한 방어는 충분하지 않다. 특히 화면 버튼 비활성화와 700ms 저장 지연은 서버의 중복 처리 방지나 원자적 저장을 대신하지 못한다.

### 익명 명단 변경과 사칭

`src/server/roster.ts:13`의 GET은 공개이며 Riot ID를 포함한 명단을 반환한다. 공개 자체가 오류라는 뜻은 아니다. 문제는 `src/server/join.ts:303–345`에서 같은 Riot ID를 알고 있다는 사실만으로 기존 사용자로 취급하고, 322–328행에서 닉네임까지 저장한다는 것이다. 입력한 Riot ID의 소유권 확인이나 해당 변경의 관리자 승인이 없다. 스트리머 화면이 열려 있으면 기존 사용자 자동 합류 처리도 실행된다.

**수정 방향:** 공개 신청만으로 저장 프로필을 수정하지 않는다. 기존 사용자의 자동 합류를 유지하려면 서버가 검증하는 본인 확인 수단을 연결해야 한다. 확인 수단이 없는 요청은 승인 대상으로 처리하는 방식도 가능하지만 기존 자동 합류 정책에 영향을 주므로 명시적으로 결정해야 한다. Riot ID나 랜덤 신청 ID 자체는 본인 인증이 아니다.

### 큐·제한 카운터·명단 쓰기 경쟁

`src/server/join.ts:63–98`의 락과 revision 검사는 get과 put 사이에 다른 요청이 들어올 수 있다. `:112`의 신청 제한과 `src/server/auth.ts:196–213`의 로그인 제한도 읽은 카운터에 1을 더해 저장하는 방식이다. 모의 KV는 읽기 결과를 얻은 뒤 다른 요청이 진행되도록 양보하게 구성했다. 이 경우 모든 요청이 같은 이전 값을 읽는 것이 실제 코드로 재현된다.

`src/server/roster.ts:36–49`와 board의 시각 비교도 검사와 저장을 하나의 연산으로 묶지 않는다. 응답을 프론트에서 무시하더라도 이미 서버 값이 덮어써진 문제는 복구되지 않는다.

**수정 방향:** 서버 측 원자적 요청 제한과 큐·명단 변경 직렬화가 필요하다. 저장에는 클라이언트 시계 대신 서버 revision과 조건부 갱신을 사용한다. 작업 ID와 저장된 결과를 연결해 재시도 시 같은 결과를 반환하도록 한다. 단순 debounce나 락 토큰 재조회만으로 완료 처리의 원자성은 보장되지 않는다.

### 연속 경기 결과 입력

`src/components/TeamPanel.tsx:84`의 승리 버튼은 양쪽 팀에 사람이 있으면 계속 활성화된다. `src/components/Board.tsx`에서 클릭마다 `recordTeamResult`를 호출하며 `src/store/createMatchActions.ts:24`는 같은 경기인지 구분하지 않고 누적한다.

**수정 방향:** 우선 동기적인 짧은 연타 방지와 처리 중 잠금으로 실수를 줄일 수 있다. 여러 탭·재전송까지 방어하려면 경기/결과 이벤트 ID가 필요하다. 같은 멤버로 다음 경기를 하는 정상 기능은 유지해야 하므로 보드 구성만으로 영구 중복 판단하면 안 된다. 관리자 ±1 보정은 여러 번 입력하는 것이 정상일 수 있으므로 경기 결과 입력과 구분해야 한다.

### 클라이언트가 보낸 데이터 신뢰

명단·보드는 배열 여부만 검사하며 updatedAt, 배열 크기, 구성원 ID 중복, 팀 정원, 관계 제약을 충분히 검증하지 않는다. 미래 updatedAt 사례는 잘못된 기기 시계로도 발생할 수 있다. 인증이 필요하므로 비로그인 원격 공격과 동일하게 취급하지는 않지만, 유출된 스트리머 토큰이나 잘못된 클라이언트 요청의 피해 범위를 넓힌다.

**수정 방향:** 본문 크기·문자열 길이·명단 크기·필드 타입·ID 유일성·팀 정원을 서버에서 검증한다. 정상 최대 인원 등 제품 기준을 정해 제한해야 한다. 이미 잘못 저장된 값을 읽을 때의 복구도 함께 필요하다.

## 코드 검토로 확인한 추가 방어 공백

- **전체 로그아웃 비밀번호 반복 시도:** `src/server/auth.ts:306`에는 로그인 제한조차 공유하지 않는다. 이전 별도 재현에서 10회 연속 실패 요청 모두 401이었다. 두 비밀번호 확인 경로에 공통 보호가 필요하다.
- **관리자 전적 보정 연타:** `src/pages/AdminApp.tsx:165`의 보정은 클릭마다 명단 전체를 PUT한다. ± 버튼에는 `syncBusy` 제한이 없고 `pushRoster`에도 동기적인 재진입 가드가 없다. 요청 직렬화·변경 합치기·revision 검사로 마지막 편집을 보존해야 한다.
- **외부 API 호출량:** `useMatchSync`의 inFlight ref는 같은 훅 인스턴스 내 동시 요청을 막지만 `src/server/matches.ts`에는 사용자별 호출 제한·중복 작업 합치기·외부 fetch timeout이 없다. 다른 탭이나 직접 요청에는 같은 방어가 적용되지 않는다. 외부 서비스 부하는 실제로 발생시키지 않았다.
- **신청 승인 후 보드 반영:** 서버가 승인/자동 합류를 완료한 후 브라우저가 보드를 저장한다. `flushBoardAfterJoin`의 실패가 사용자에게 전달되지 않고 재시도 결과도 확인하지 않는다. 창 종료나 연결 실패가 그 사이에 발생하면 승인 완료와 실제 보드가 달라질 수 있다. 승인과 입장 반영을 재시도 가능한 서버 작업으로 연결하는 것이 필요하다.
- **신뢰 기기:** `src/server/auth.ts:179`는 요청의 `X-Device-Id`가 등록되어 있으면 세션 폐기 epoch 검사를 건너뛴다. 토큰 서명·만료 검사는 유지되므로 헤더만으로 로그인할 수 있는 것은 아니다. 다만 등록 기기 ID와 아직 만료되지 않은 폐기 토큰을 가진 경우 예외를 다른 기기에서 재사용할 수 있다. ID는 기기 증명이 아니므로 기기 결합·예외 폐기 정책을 검토해야 한다. UUID를 모르는 공격자가 추측할 수 있다고 주장하는 것은 아니다.
- **입력 실패 처리:** 이전 점검에서 null/숫자 비밀번호가 TypeError를 발생시켰다. 잘못된 JSON 스키마·손상된 경로 인코딩·매우 긴 문자열을 정상 4xx로 거절하는 경계 검증이 필요하다.
- **저장 수명:** 신청 상태와 요청 제한 키에 애플리케이션이 expirationTtl을 설정하지 않는다. 새 IP·새 신청이 누적될 때 보존 정책이 필요하다. 실제 저장 한도 도달은 재현하지 않았다.

## 정상 작동을 확인한 방어

- 비로그인 명단·보드 PUT은 401.
- 스트리머 토큰으로 관리자 설정 PUT은 401.
- 순서대로 잘못된 비밀번호를 입력하면 9번째 로그인 요청은 429.
- 순서대로 같은 신청을 제출하면 두 번째는 409.
- 승인·거절 핸들러에는 동일 화면의 같은 신청에 대한 ref 기반 실행 가드가 있다. 전적 동기화에도 inFlight ref가 있다. 이 가드는 다른 탭과 직접 API 요청까지 막지는 않는다.
- 토큰은 HMAC 서명·역할·만료를 검사한다. 숨겨진 관리자 버튼이 서버 권한 검사의 유일한 방어는 아니다.
- 닉네임 등은 확인한 화면에서 React 텍스트로 렌더링하며 `dangerouslySetInnerHTML`, eval, 직접 innerHTML 사용은 src 검색에서 발견하지 못했다. 이것만으로 모든 XSS 가능성을 배제한 것은 아니다.

## 기능·UI를 최대한 유지하는 보완 순서

1. 익명 신청의 기존 명단 변경 차단, 모든 비밀번호 확인 경로의 요청 제한 강화.
2. 큐·명단·카운터의 원자적 처리와 중복 요청 결과 재사용.
3. 경기 결과 연타 방지, 관리자 저장 요청 직렬화, 오래된 응답 무효화.
4. 서버 입력 크기·스키마 검증과 서버 revision 도입.
5. 실패한 승인/보드 반영 재시도, 외부 API 제한·timeout, 상태 데이터 만료 정책.

1번의 본인 확인 정책과 2·4번의 저장 구조는 구현 전에 기존 자동 합류·동시 편집의 기대 동작을 유지하도록 설계해야 한다. 이번 작업에서는 검토 결과와 재현 스크립트만 추가했으며 보안 문제가 수정됐다고 볼 수 없다.
