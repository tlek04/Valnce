- 테스트 통과는 기존 기준과의 일치를 뜻하며, 아래 오류가 없다는 뜻은 아니다.

## 우선 수정할 문제

### 1. [P1 / 실행 재현] 한 번 저장한 뒤 보드·명단 원격 폴링이 멈춤

위치: `src/hooks/useBoardSync.ts:54`, `:144`; `src/hooks/useRosterSync.ts:34`, `:103`.

700ms 타이머가 실행된 뒤에도 `pushTimer.current`를 null로 지우지 않는다. 이후 모든 pull이 `if (pushTimer.current) return`에서 종료된다. 성공적으로 저장한 뒤에도 다른 기기의 변경과 신규 명단을 받아오지 못한다. 재현에서 초기 GET 1회, PUT 1회 후 poll을 실행해도 GET은 1회 그대로였다. 실패한 저장 이후에도 같은 문제가 생긴다.

수정 방향: 타이머 시작 시 대기 핸들을 비우고, 진행 중인 업로드와 미전송 변경은 별도 상태로 보호한다. 핸들만 비우면 업로드 중 pull이 로컬 변경을 덮을 수 있으므로 요청 세대·로컬 변경 여부도 함께 검사해야 한다. UI 변경 불필요.

### 2. [P1 / 실행 재현] 24시간 지난 참여 횟수가 다시 현재 시각으로 생성됨

위치: `src/utils/playCount.ts:16–23`.

`readPlayAts`는 기존 시각을 모두 만료시킨 뒤 결과가 비면 `playCount`를 구버전 값으로 간주하여 현재 시각으로 복구한다. `{playAts: [25시간 전], playCount: 1}`을 넣으면 빈 배열 대신 `[현재 시각]`을 반환한다. 정상 최신 데이터에도 구버전 변환이 적용되어 과거 참여가 새 참여로 되살아나고 추첨 가중치에 영향을 준다.

수정 방향: `playAts` 필드 자체가 없는 구버전에만 변환을 적용한다. 유효 배열이 있으나 모두 만료된 경우는 0회로 유지한다. 장시간 열린 보드에서도 선발 직전 시각을 기준으로 횟수를 다시 계산하는지 함께 보완한다.

### 3. [P1 / 실행 재현] 전체 로그아웃 API가 비밀번호 시도 제한을 우회하는 경로

위치: `src/server/auth.ts:306–326`.

로그인에는 15분/8회 제한이 있지만 `/api/auth/revoke-all`은 관리자 비밀번호를 직접 비교하면서 시도 제한을 적용하지 않는다. 잘못된 비밀번호 10회 연속 요청이 모두 401이며 429로 제한되지 않았다. 로그인 제한과 무관하게 관리자 비밀번호를 계속 대입할 수 있는 별도 경로다. 실제 비밀번호나 운영 서버를 사용하지 않고 메모리 KV와 테스트 비밀번호로 확인했다.

수정 방향: 비밀번호 확인이 필요한 두 경로에 공통 제한을 적용한다. 외부에서 별도로 적용된 WAF 제한 유무는 확인하지 않았다.

### 4. [P1 / 코드 경로 확인] 참가 큐의 락과 승인 명단 저장이 동시 요청을 직렬화하지 못함

위치: `src/server/join.ts:63–98`, `:470–474`, `:542`.

두 요청이 동시에 빈 락을 읽으면 각각 락을 쓴 뒤 모두 본문에 진입할 수 있다. revision 확인과 저장도 별도 get/put이므로 둘 다 같은 revision 검사를 통과할 수 있다. 또한 승인에서는 큐 제거 락을 해제한 뒤 외부 티어 조회와 명단 전체 저장을 수행한다. 서로 다른 두 신청 승인이 같은 명단을 읽고 각자 전체 배열을 쓰면 한쪽 플레이어가 유실될 수 있다. 메모리 KV를 순차 실행하는 기존 테스트는 이 요청 교차를 검증하지 않는다.

수정 방향: 큐와 명단 변경을 서버 측에서 원자적으로 직렬화하는 저장 경로를 마련한다. 클라이언트 버튼 비활성화나 락 토큰 재확인만으로는 충분하지 않다. 실제 운영 환경 재현은 하지 않았으므로 발생 빈도는 알 수 없다.

### 5. [P2 / 실행 재현] 가능한 5대5 조합이 있는데 자동 밸런스가 불가능하다고 반환

위치: `src/utils/balance.ts:376–394`.

3·3·3·2·2명 동맹 그룹에서 난수를 0으로 고정하면 앞의 3개 그룹으로 9명을 뽑고 남은 그룹이 맞지 않아 실패한다. 같은 입력에서 3·3·2·2를 참가자로 고르면 실제 함수가 5대5에 성공한다. 실패 메시지는 조건상 불가능한 것처럼 안내하지만 원인은 선발 조합을 재탐색하지 않는 데 있다.

수정 방향: 현재 가중 추첨을 유지하면서 실패한 선발의 대안 조합을 탐색한다. 참가 결과와 확률에 영향을 주므로 점수 공식·선발 정책을 무심코 바꾸지 않도록 별도 검증한다.

### 6. [P2 / 실행 재현] 유효한 JSON이지만 타입이 잘못된 요청은 400 대신 예외 발생

위치: `src/server/auth.ts:271–279`; 유사 처리: join, matches, roster, board, siteSettings.

로그인 본문 `null` 또는 `{password: 123}`은 JSON 파싱에 성공한 뒤 `body.password`/`.trim()`에서 TypeError가 난다. Worker에 이를 정상 오류 응답으로 바꾸는 공통 처리가 없다. 다른 API도 TypeScript 형변환을 런타임 검증 대신 사용한다. 명단·보드 PUT은 배열 여부만 확인하여 구성원 스키마·중복 ID·정원을 검증하지 않는다.

수정 방향: 본문을 unknown으로 받아 객체·필드 타입과 허용 범위를 검사하고 400 응답을 반환한다. 정상 사용자 입력과 UI는 유지할 수 있다.

### 7. [P2 / 실행 재현] 손상된 명단 저장값이 재수화를 중단시킴

위치: `src/store/persistence.ts:8`.

`hydrateLibrary({players: {}})`는 배열이 아닌 값을 순회하면서 TypeError를 던진다. 이 복원이 중단되어 persist hydration이 완료되지 않으면 `onFinishHydration`을 기다리는 동기화도 시작되지 않을 수 있다.

수정 방향: 배열 여부를 먼저 확인하고 손상된 저장값에서 명단 복원을 안전하게 완료하도록 한다. 오류를 감지한 경우 원본 복구 가능성을 남기는 것이 좋다.

## 유지보수·검증 공백

- 기존 테스트는 계산·스토어·서버·API·UI 기준과 의존성 경계를 확인하지만 훅의 타이머 완료, 통신 실패 후 복구, 언마운트 중 응답, 다중 클라이언트 동시 쓰기를 검증하지 않는다. 1번 오류가 기존 테스트를 통과한 이유다.
- 두 sync 훅은 cleanup에서 비동기 응답을 무효화하지 않는다. 이전 화면의 요청이 완료되어 스토어를 갱신하거나 재시도 타이머를 예약할 수 있는 경로도 함께 정리할 필요가 있다.
- `ARCHITECTURE.md`와 `REFACTOR_VALIDATION.md`에는 현재 코드와 다른 설명이 남아 있다. 특히 승인 저장 순서는 현재 큐 선제 제거 후 명단 저장이며, 원격 명단은 현재 보드의 일부 프로필을 갱신한다. 과거 설명만 근거로 안전성을 판단하면 안 된다.
- 이번 점검으로 전체 코드의 모든 실행 조합이나 무결함을 보증하지 않는다. 기능·UI 변경 없이 먼저 1·2·3·6·7을 고치고, 동시성 저장 경로와 선발 재탐색은 별도 회귀 검증을 붙이는 순서가 적절하다.
